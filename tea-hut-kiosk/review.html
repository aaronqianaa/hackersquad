Tea Hut Android · Square Draft v1 — for review

Self-Ordering Kiosk
Build Plan

Staff sign in, pick a branch, and hand the screen to the customer. Orders, menu, and payment all run through Tea Hut's existing Square account — the kiosk is a new ordering surface, not a second POS to reconcile.

01 — Read this first

Three findings that shape everything

These came out of studying how Square actually permits kiosks to be built. Each one is a constraint, not a preference — they should be settled before anything else in this plan is worth debating.

FINDING 01

The touchscreen TV cannot take the card payment

Square's Mobile Payments SDK and the older Reader SDK both state that using them for unattended terminals or kiosks is strictly prohibited. We cannot put a Square reader on the TV and charge the card in our own app.

The supported path is the Terminal API: our app builds the order, then sends a checkout request to a paired Square Terminal next to the screen. The customer taps or dips there; the Terminal handles the card, the tip, and the printed receipt. This is how the published Square kiosk integrations work.

→ Each kiosk lane = 1 Android touchscreen + 1 Square Terminal.
→ Card data never enters our app, which keeps Tea Hut out of PCI scope.

FINDING 02

The Square connection lives on a server, not on the tablet

Square access tokens expire in 30 days. A refresh token obtained through the authorization-code flow does not expire and can be exchanged for new access tokens indefinitely — so we deliberately use that flow rather than PKCE, whose refresh tokens are single-use and die after 90 days.

A small backend holds the client secret and refresh token and renews on a schedule. The kiosk device stores no Square credential at all. A backend is required regardless, because Square's Terminal and Order webhooks need a public HTTPS endpoint and a tablet cannot be one.

→ Authorize once, then it stays connected. No one re-links it every month.
→ A stolen kiosk leaks nothing; revoke that one device and carry on.

FINDING 03

Staff accounts and branch selection are ours to build

Square's team permissions do not express "which kiosk is pointed at which store." So we own user accounts, roles, which branches a user may operate, and the device-to-branch binding. Branch selection is backed by Square Locations — one location per Tea Hut branch — so every order lands in the right store's Square dashboard.

02 — Architecture

How the pieces connect

The kiosk never talks to Square directly. Everything routes through the backend, which is the only place a Square credential exists.

Stack, and why

  • Android app — Kotlin + Jetpack Compose, native. Kiosk lockdown (device-owner APIs, lock task mode, custom launcher, boot receiver) is native-only territory, and a cheap in-cell panel may ship without Google Play Services. Flutter or React Native would add risk here for no gain.
  • Backend — FastAPI + Postgres + Redis. Matches the stack already running in this organization, so there is no new runtime to learn or operate.
  • Admin console — server-rendered web, on the same backend. Staff use it from a laptop or phone; it does not need to be a separate app.

One order, end to end

attract screen→ dine-in / take-out→ menu (local cache)→ customize→ cart→ member lookup→ CreateOrder→ Terminal checkout→ webhook→ order number→ KDS ticket

03 — References

What we take from Chowbus and MenuSifu

Both are built for Asian-cuisine restaurants and are the closest reference for a bubble tea shop. Their published feature sets line up almost exactly with what Tea Hut needs.

PatternWhy it matters for Tea Hut
Deep combo & modifier logicBubble tea is modifier-heavy: size, ice level, sugar level, multiple toppings with limits
Real bilingual operationNot a translation bolted onto an English-first system — EN + 中文 as a first-class mode
Loyalty sign-up inside checkoutBoth report this moment as the highest-converting place to ask
Timed upsell promptsAdd-ons, combo upgrades and premium bases, offered at the right beat — directly moves average order value
Live sync to POS, KDS, inventoryOrders reach the bar without anyone re-keying them
Dine-in vs take-out up frontDrives fulfillment type, packaging and tax behavior

On copying: we replicate these interaction patterns and flows, which are industry-standard and not owned by any one vendor. We won't copy their code, image assets, fonts, icon sets or trademarks — the app carries Tea Hut's own branding. The result is functionally equivalent without importing anyone else's IP into Tea Hut's product.

06 — Risk

What could go wrong

Square doesn't approve the unattended-kiosk deployment Blocks the project

Resolve in Phase 0, in writing, before any code is written. Fallback: an attended framing, or Square's own first-party Kiosk product.

The in-cell TV can't be set as Android device owner Verify on hardware

Without device owner there is no true lockdown and customers can exit the app. Fallback is replacing the home launcher plus immersive mode and navigation blocking — weaker, but workable. Must be tested on the real unit.

Panel ships without Google Play Services Designed around

No FCM push and no Play updates. The plan already assumes this: WebSocket or polling for push, and a self-hosted APK update channel.

Hardware is landscape-locked Designed around

Both layouts get built from day one; which is primary is decided in Phase 0 after seeing the unit.

Network drops mid-order Designed around

The menu is served from local cache so browsing survives. New checkouts are blocked with a clear "please order at the counter" message. A payment is never queued locally.

Modifier pricing drifts between kiosk and counter Designed around

Square Catalog is the single source of truth. Kiosk overrides may change presentation — name, photo, ordering, visibility — but never price.

07 — Decisions needed

Open questions for Tea Hut

The four below block Phase 0. A longer list of design-shaping questions is in docs/OPEN-QUESTIONS.md.

Has Square approved this deployment?Q1

Written confirmation from Square developer support that a Tea Hut kiosk lane qualifies for the Terminal API path. If the answer is no, the payment architecture changes entirely.

What is the exact model of the smart TV?Q2

Needed to test three things on the real unit: can it be set as device owner, does it ship with Play Services, is it landscape-locked in hardware.

Does Tea Hut already own Square Terminals?Q3

One is required per kiosk lane. If they need purchasing, that is lead time on the critical path.

How many branches, and how many lanes each?Q4

Drives the pilot plan, the device registry design, and the hardware budget.

Also worth answering before Phase 3

  • Is there an existing Square loyalty program to connect to, or does one need creating?
  • Where does the order ticket go — Square KDS, a LAN printer at the bar, or the Terminal's receipt only?
  • Is dine-in just "pickup when your number is called," or do you want table numbers?
  • Should the kiosk prompt for tips at all? Some tea shops skip it to keep the line moving.
  • Does Square Catalog already carry Chinese item names, or do translations live in our override layer?
  • Are there existing product photos? The kiosk is photo-driven — menu photography is the single biggest visual quality factor.
